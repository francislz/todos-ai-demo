1. Context and goal

Todos are a single flat list today, so there is no way to focus on one subject (work, personal, travel, vacation-prep). This issue adds labels: a managed list of colored labels (create, rename, recolor, delete), assignable to any todo at any time, and a filter that narrows the list to the chosen labels.

Acceptance (from the issue): I can assign labels to my todos; I can filter my todos by labels; I can create new labels.

Decisions already made by the owner (binding)

  1. Labels are their own entity with a managed list (create, rename, delete) with colors.
  2. Names are unique case-insensitively ("Work" equals "work"), at most 30 characters; at most 10 labels per todo.
  3. Labels can be added to and removed from existing todos at any time.
  4. A multi-label filter matches any selected label (OR).
  5. There is a "No label" filter, and the filter state lives in URL query parameters.

2. API contract (closed)

Implementers work in parallel from this section. Everything not listed is unchanged. All bodies are JSON. Error body is unchanged: { "error": { "code": string, "message": string } }. Malformed JSON stays 400 VALIDATION_ERROR. Unknown body fields are ignored, as today.

2.3 Semantics

  • labelIds in a todo body (POST and PATCH): must be an array of strings; duplicates are removed silently (first occurrence wins); at most 10 after de-duplication; every id must be an existing label. The value replaces the todo's whole label set ([] clears it). The stored and returned order is the order sent.
  • PATCH /api/todos/:id: fields that are absent are left untouched. completed behaves exactly as today (completedAt set or cleared only when the value actually changes). Sending the current values is a successful no-op. Completed todos can be labelled too. Validation runs before the existence check, as today (an invalid body on a missing todo is 400).
  • POST /api/labels: name is normalized (section 3.2) and must be unique case-insensitively. When color is omitted the server picks the palette color used by the fewest labels (ties: palette order, so the first label is gray). Limit check (50) happens before the uniqueness check is reported: with 50 labels the answer is always LABEL_LIMIT_REACHED.
  • PATCH /api/labels/:id: renaming a label to a different casing of its own name is allowed ("work" to "Work"). Renaming to another label's name (any casing) is 409. The label id never changes, so todos and bookmarked filter URLs keep working.
  • DELETE /api/labels/:id: removes the label and strips its id from every todo's labelIds in the same atomic write. No todo is deleted. A second delete of the same id is 404.
  • Filtering is not part of the API. GET /api/todos always returns every todo; the web client filters.

3.2 Label name rules

  1. Normalize (in this order): Unicode NFC, trim, collapse every run of whitespace to one space. " Vacation prep " becomes "Vacation prep".
  2. Validate the normalized value: not empty; at most 30; matches LABEL_NAME_PATTERN (Unicode letters and digits, space, and - _ & ' . /; first character a letter or digit). Valid: work, vacation-prep, R&D, Q3/2026, Mom's stuff, Férias, 2026. Invalid: -work, #urgent, a,b, emoji, control characters.
  3. Uniqueness key: labelNameKey(name) = name.normalize('NFC').toLowerCase(). Two labels may not share a key. The stored name keeps the casing the user typed.
  4. Ordering: ascending by uniqueness key using plain code-unit comparison. It is deterministic on server and browser (no locale tables, so no hydration mismatch); the trade-off is that accented letters sort after z.

3.3 Color palette

The stored value is the key. The web app maps each key to three CSS variables (--label-<key>-bg, -fg, -border) in globals.css. 3.4 Persisted file and backward compatibility

Still one JSON file (apps/web/.data/todos.json or TODOS_DATA_FILE), now with a second top-level key:

{
  "labels": [
    { "id": "77aa…", "name": "travel", "color": "blue", "createdAt": "2026-11-19T10:00:00.000Z" }
  ],
  "todos": [
    { "id": "41c2…", "title": "Book flights", "completed": false,
      "createdAt": "2026-11-19T10:05:00.000Z", "completedAt": null, "labelIds": ["77aa…"] }
  ]
}
  • Normalize on read, in one function (normalizeStoreData): missing or non-array labels becomes []; missing or non-array todos becomes [] (as today); a todo without labelIds gets []; ids in labelIds that match no stored label are dropped (protects against hand-edited files). A missing file is an empty store (as today).
  • No migration step and no version field. An existing file from main is read as "no labels, every todo unlabelled". Reads never write; the file is rewritten in the new shape by the first mutation.
  • Guarantee to the API: every Todo leaving the service has labelIds, and every id in it refers to an existing label.
  • Rollback caveat: the code on main today reads the new file fine but would drop the labels key on its next write. Rolling back after labels were created loses them (section 7).

The persistence port and atomicity

interface StoreData { todos: Todo[]; labels: Label[] }

interface TodoStore {
  /** A normalized snapshot; callers may mutate it freely (it is a copy). */
  read(): Promise<StoreData>;
  /**
   * Runs `work` on a private draft, serialized with every other transaction of this store.
   * If `work` returns, the draft is persisted (file: temp file + rename); if it throws, nothing is written.
   * `work` is synchronous.
   */
  transaction<T>(work: (draft: StoreData) => T): Promise<T>;
}
  • One store instance owns the file and its write queue; both services receive the same instance. There are never two writers on the file.
  • Every rule that reads and then writes runs inside one transaction: label delete + cascade, name uniqueness + insert, total-limit + insert, "label ids exist" + todo write. Concurrent requests cannot create duplicate names or dangling ids.
  • Business rules stay in the services (the store has no knowledge of labels vs. todos beyond the data shape). Services throw domain errors from inside work, which aborts the write.
  • InMemoryTodoStore deep-copies on read and commits a deep copy on success (fixes the shared-array hazard a shallow { ...todo } copy would have with labelIds).
  • Service deps: { store, now?, generateId? } for both services (same injectable clock and id generator as today).

State and URL sync

  • Source of truth: todos and labels live in client state seeded from the server render (as todos do today); the filter lives only in the URL.
  • URL format: ?label=<id>&label=<id>&label=none. Written in label order, then none. No filter means no label parameter. Other query parameters are preserved. Values that are neither a known label id nor none are ignored when reading and disappear on the next write.
  • Writing: window.history.replaceState(null, '', url). Next.js integrates it with useSearchParams, and unlike router.replace it does not re-run the force-dynamic server page on every chip click. Filter changes replace the history entry (they do not add Back steps). Reload, bookmarks and shared links restore the filter.
  • Matching: no filter shows everything. Otherwise a todo is visible when it has any selected label, or when "No label" is selected and it has none.
  • Derived values: visible todos, counter (visible open / done), "Showing X of Y todos", and per-label usage counts in the panel (computed from all todos, not the filtered ones).
  • Add form pre-labelling: the form's label selection starts as the filtered label ids and is reset to them whenever the filter changes and after each successful add. The user can change it before adding. If an added todo still does not match the filter, the notice of mockup M12 is shown until the next action.
  • After a label delete: remove it from label state, strip it from local todos (removeLabelFromAll), drop it from the filter and from the form selection. After a rename or recolor only label state changes.
  • Errors: todo actions (add, toggle, set labels, delete) use the existing card-level error-banner. Label management errors are shown inside the panel (label-error).
  • Loading: there is no client loading state; data arrives with the server render and the Suspense fallback is null.

5.2 Filter active (OR) and "No label"

URL for this state: /?label=<travel-id>&label=none. Pressed chips are filled with the label color and prefixed with a check mark (state is not conveyed by color alone). A summary line appears with Clear filter. The counter counts the visible todos. The add form is pre-labelled with the filtered labels (here: travel).

5.3 Label picker (per-todo editing and add form)

One LabelPicker component, used in both places. It is a non-modal popover anchored under the trigger: a checklist of all labels (alphabetical), Cancel and Apply. Nothing is saved until Apply; Esc, Cancel or a click outside discards. On a todo, Apply closes the popover and sends one PATCH (the row is busy at 60% opacity until it returns). In the add form, Apply only updates the form selection. On mobile the popover spans the full row width.

5.4 Manage labels panel

An inline panel inside the card (not a modal), toggled by Manage labels / Close labels (aria-expanded). Create row on top, then one row per label (alphabetical) with its usage count. Only one row at a time can be in edit or delete-confirmation mode.

5.7 Behavior and states

  • Busy: a todo row whose labels are being saved is aria-busy at 60% opacity with its controls disabled (existing pattern). Panel buttons show their busy copy and the row's controls are disabled while a label request is pending.
  • Errors: a failed label save on a todo shows the card error-banner and the chips stay as they were. A failed panel action shows label-error under the create row; the row stays in its edit or confirm mode so the user can retry or cancel.
  • Chips on a todo are not interactive; long names truncate with an ellipsis inside the row width. A completed todo keeps full-color chips (only the title is struck through).
  • Color picker: 8 round swatches; the selected one has a 2px ring and a check mark. In the create row the preselected color is suggestLabelColor(labels).
  • Picker limit: when 10 labels are checked the remaining checkboxes are disabled and the hint is shown.
  • Mobile (max-width 480px): card padding 16px; the labels bar wraps and the manage button goes to its own line; the picker spans the row; panel create and edit rows stack. No horizontal scrolling at 360px and up.

5.8 Accessibility

  • Filter bar: role="group" with aria-label="Filter by label"; each chip is a <button aria-pressed> whose name is the label name (or No label).
  • Manage toggle: <button aria-expanded aria-controls="label-manager">. The panel is a <section aria-labelledby>. Opening moves focus to the new-label input; closing returns it to the toggle.
  • Picker: the trigger is a <button aria-haspopup="dialog" aria-expanded> named Edit labels of "{title}" on a todo and Labels for the new todo in the form. The popover is role="dialog" (non-modal) with the same name, containing a <fieldset> of native checkboxes. Focus moves to the first checkbox on open and back to the trigger on close; Esc cancels.
  • Chips: the todo's chips are a <ul aria-label="Labels">.
  • Color picker: role="radiogroup" with aria-label="Color"; each swatch is a native radio input whose label is the color key (visually hidden text).
  • Panel rows: buttons named Edit label "{name}", Delete label "{name}"; the rename input is labelled Label name. The delete confirmation moves focus to its Cancel button. label-error and error-banner are role="alert"; the filter summary and the notice are role="status".
  • Focus: a visible :focus-visible outline (2px --primary, 1px offset) on every button, chip, checkbox and swatch. Touch targets for filter chips and row buttons are at least 28px tall with 6px gaps.

7.1 Risks

RiskMitigation
Rollback after labels exist: the pre-labels code drops the labels key on its next write.Documented in the PR; the data file is local, git-ignored demo data. Back up .data/todos.json before a rollback.
R1 changes a core port; the diff of the core PR is larger than a pure feature diff.R1 is its own commit that first ports existing behavior with the existing tests green, before any label code.

Up to 50 filter chips wrap into several lines on mobile.Accepted for v1 (wrapping keeps every chip reachable and testable). A collapsible filter can be a follow-up issue if it becomes a problem.
